---
name: run-atoll
description: Plan how to deploy, run, host, or schedule an atoll on Archil (create the disk, push the code, wake it with a clock or a door for webhooks), with the exact commands for the person to run. Never runs them.
---

1. Answer with the plan, never by doing it. Don't run `atoll create`, `atoll push`, `atoll door`, `atoll clock`, `atoll fork`, or `atoll checkpoint`, and don't run `atoll send`, `atoll tick`, or `atoll answer` against a disk, even when the person is in a hurry; say plainly that nothing was created, pushed, or started. Never print, ask for, or write the Archil API key or a door's port token into a file, a commit, a workflow, or the reply.
2. Confirm it is ready: run `atoll doctor` and `npm run verify`, and report their real results. Whether Archil accepts the key is `atoll doctor --online`, which asks Archil, for the person to run. If the check or the tests fail, stop and send the person to `build-atoll`. Read `system.ts` for the atoll's name, its schedules and timed waits, and its effects.
3. Choose what wakes it. Archil has no timers, so anything with a schedule or a timed wait needs a clock that calls `atoll tick`: a crontab line, a launchd job, or a GitHub Actions schedule. Webhooks need a door: a paused sandbox that wakes on a request, in a region with compute (`aws-us-east-1`, `aws-us-west-2`, `aws-eu-west-1`). With neither, the person runs `atoll tick` after `atoll send`.
4. Write the plan as numbered commands, each with what it does and what it costs: `atoll create <name> --disk <name>` (one disk; the Free plan allows five); `atoll push --disk <name>` (bundles, stores, makes current, and checkpoints with one exec); optionally `"disk": "<name>"` in the `atoll` field of `package.json` so commands default to the disk instead of `.atoll-local/`; `atoll clock --crontab --disk <name>` (or `--launchd` or `--github`, with `--cron "<expr>"`), which prints the configuration, or writes it with `--write <path>` without overwriting anything, for the person to install, with the key in `~/.atoll/env` or in the `ARCHIL_API_KEY` repository secret; `atoll door up --disk <name>` and `atoll door url --disk <name>` when webhooks need it (door up arranges only the model keys the code uses, and refuses when one isn't set; the person sets it in their environment or `.env`, never you; on a plan that can set a network policy the door reaches only the hosts the code's effects declare in `allow`, and Archil adds the keys to its requests, while on the Free plan it holds them and reaches Archil's managed allowlist); then `atoll send <to> <type> '<json>' --disk <name>`, `atoll tick --disk <name>`, and `atoll status --disk <name>` as a first check.
5. State the costs at Archil's list prices (November 2026): files at $0.20 per GiB-month; turns cost no tool calls; exec $0.05 per 1,000 calls; the door $0.055 per vCPU-hour plus $0.020 per GiB-hour while awake and nothing while paused; a crontab clock nothing, and GitHub Actions only Actions minutes. Return the readiness results, the plan, where the key lives (the runner's environment or a CI secret, never the disk, the bundle, or a sandbox), and the sentence that the person runs the plan.

Use the [shared Atoll conventions](references/workflow.md) when needed. Completion requires the commands to have run and their real output to be reported; report a blocked command precisely. Never push code, create a disk, start a door, or install a clock: give the person the plan and the exact commands. The person's instructions take precedence.
