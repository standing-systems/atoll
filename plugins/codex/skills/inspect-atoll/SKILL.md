---
name: inspect-atoll
description: Explain what an atoll is doing, why it did something, what it is waiting for, or what it needs from me, from `atoll status`, `atoll why`, `atoll log`, `atoll asks`, and the files on its disk. Says unknown where the journal ends.
---

1. Name the atoll the question is about: a local one (`--dir <path>`), a disk (`--disk <name-or-id>`), or a fork's branch ID. In a project, commands without either flag read `.atoll-local/`, or the disk `package.json` names. Read only: don't run `atoll send`, `atoll tick`, or `atoll answer`, and don't edit the atoll's files. Answering an ask is the person's decision; give them the exact `atoll answer <ask-id> <option>` command, and say that it ticks right after.
2. Answer with the command that fits: `atoll status`, or `atoll status <address>` for one part, for the five answers (what it is for, what changed and why, what it waits for, the evidence, and what it needs); `atoll why <path|event-id|seq>` for the turn behind something and its cause chain back to an outside event; `atoll log --since 1d` or `--part <address>` for what happened lately; `atoll asks` for the open questions with their options, defaults, and expiry.
3. Follow the evidence: each `sha256:<hex>` is a file at `evidence/<first two hex digits>/<hex>`, with its source, type, time, and size in `<hex>.json`. Cross-check with the files: for a local atoll or a mounted disk, `cat parts/<address>/waiting.json`, `tail -n 5 journal/<day>.jsonl`, `ls asks/ outbox/`, and `grep -rl <term> evidence/`; for a disk you can't mount, which on the Free plan is any disk from your own machine, `atoll ls asks/ --disk <name>` and `atoll cat parts/<address>/waiting.json --disk <name>` read the same files through the object API.
4. Explain in the order things happened: what started it (the owner, the clock, the door, another part, or an effect's result), which part decided what and why (its recorded note and the handler code), what came of each effect, and where the path ended. Quote event IDs, sequence numbers, effect IDs, ask IDs, and evidence references exactly. An effect `in-doubt` may or may not have happened; never report it as either. When `atoll why` can't reach an outside event, the record ran out: say "unknown" and where it ends.

Use the [shared Atoll conventions](references/workflow.md) when needed. Completion requires the commands to have run and their real output to be reported; report a blocked command precisely. Never push code, create a disk, start a door, or install a clock: give the person the plan and the exact commands. The person's instructions take precedence.
