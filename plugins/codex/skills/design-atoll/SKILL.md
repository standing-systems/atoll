---
name: design-atoll
description: Design an atoll, a standing agent that watches something, follows up, reminds me, or asks me before acting, as a table of parts (what each owns on disk, waits for, asks me, may do in my name, and spends) plus a CHARTER.md in my voice with a "never do" list. Do not use for generic architecture discussions.
---

1. Restate what the person wants kept standing in two sentences, in their words. List what it watches, what it tracks, what it waits on, who it might contact, and what it might spend. If there is no project yet (`system.ts` and `CHARTER.md` at its root), set one up first with `setup-atoll-project`.
2. Draft one row per part: its address (`watch/<package>` for a part with one directory per instance), its purpose as a plain sentence in the owner's voice, the files it owns under `parts/<part>/`, what it waits for (a time, an event type, an ask's answer, or a schedule), what it asks the owner (options with consequences, a recommendation, a default, an expiry), what it may do in the owner's name (each effect with its kind, approval, and whether a retry is safe), and its budget.
3. Argue for fewer parts. A part earns its own directory only if it owns state no other part writes, has its own waits or schedule, or needs its own instances. Anything else is a handler on an existing part, a file in its directory, an effect, or a schedule. Parts read each other's files freely, so sharing data needs no part or event. Splitting buys no parallelism: one runner handles an atoll's events at a time. For each part you keep or drop, name the `@standing-systems/atoll/testing` test that would settle a disagreement.
4. Apply the promises: every effect that reaches another person or speaks for the owner has `approval: true`; every effect that costs money or counts against a plan has a budget; models propose and code decides; every ask has a default and an expiry. Never promise exactly-once external effects, ordering across senders, or exact timing.
5. Write `CHARTER.md` in the owner's voice, first person, in the shape `atoll push` will write to the disk from the system's charter and its parts' purposes: the title `# <atoll name>`; then the sections What I want, What it may do in my name (each effect in everyday words, with its allowance), What it must never do (a short list), and How it asks me (what it asks about, and what happens if nobody answers); then `## Parts`, one line per part, `- **<part>**: <purpose>.`, with no closing period in the purpose itself. Write no handlers or tests yet; that is `build-atoll`.
6. Return the parts table, the effects list, the charter, the rejected parts with what each became, and the assumptions that could be wrong (volumes, what an outside API guarantees, how the owner wants to be asked). Stop and ask when a consequential choice is open: who it may contact, what it may spend, or what must never be lost.

Use the [shared Atoll conventions](references/workflow.md) when needed. Completion requires the commands to have run and their real output to be reported; report a blocked command precisely. Never push code, create a disk, start a door, or install a clock: give the person the plan and the exact commands. The person's instructions take precedence.
