---
name: build-atoll
description: Write or change an atoll's handlers, effects, schedules, waits, and asks in system.ts, with tests against a local atoll using @standing-systems/atoll/testing, then `atoll check`. Use when implementing an atoll design or adding behavior to an atoll.
---

1. Run `atoll check` and read `system.ts`, `CHARTER.md`, and the existing tests. Fix every error before adding anything. Change the declaration first: the parts and their purposes, `instances`, `schedules`, `effects` with their kind, `approval`, `idempotent`, `budget`, and `allow` hosts, and the `charter`, which holds the words of `CHARTER.md` between its title and `## Parts`. `atoll push` writes the disk's `CHARTER.md` from the charter and the purposes, so keep the project's file identical to that, and keep the test that checks it.
2. Write handlers with the Turn API. Handlers never reach outside: no `fetch`, no `Date.now()` or argument-less `new Date()`, no `Math.random()`, no timers, no `process.env`, and no network, process, or file system imports. All I/O is a declared effect requested with `t.effect(...)`, whose result comes back as an event with the body `{ ok, effect, name, result, error, denied }`; check `ok` first and treat anything else as not done. An http answer is `ok` whatever its status, so check `result.status`, and give a polled request `pick: [...]` so the result keeps only the fields the handler reads. The time is `t.now`. A handler writes only under its own part's directory and may read anything. Every part is waiting for something or done: the waits a turn declares with `t.wait` replace the part's earlier ones, a turn that declares none keeps those its event didn't satisfy, and schedules re-arm by themselves until `t.done`.
3. Assume the same news arrives twice under new event IDs: the runtime dedupes event IDs, not business events, so dedupe by the business key in the part's own files. Declare `idempotent: true` only when the destination honors the key (`ctx.key` in a custom effect's `run`). Check model output's shape before acting on it.
4. Keep the existing tests as they are, and add one focused test per requested behavior with `testAtoll` from `@standing-systems/atoll/testing`: stub every effect a test reaches, move time with `s.advance`, approve, deny, or let an approval expire with `s.answer` and `s.advance`, and assert that `(await s.status()).idle` is empty.
5. Run `npm run verify` (`atoll check`, then the tests) and fix what fails. Each `atoll check` warning needs a fix or a reason; a custom effect's `run` isn't scanned, since outside calls belong there. To watch it by hand, use only the local atoll, with `--dir .atoll-local` on `atoll push`, `atoll send`, `atoll tick`, and `atoll status`; effects really run there. Report the real results.

Use the [shared Atoll conventions](references/workflow.md) when needed. Completion requires the commands to have run and their real output to be reported; report a blocked command precisely. Never push code, create a disk, start a door, or install a clock: give the person the plan and the exact commands. The person's instructions take precedence.
